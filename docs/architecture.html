Factory Inventory Management System

A demo supply-chain dashboard built as a two-tier application: a Vue 3 single-page client talking over plain HTTP/JSON to a Python FastAPI service that serves filtered, Pydantic-validated slices of an in-memory dataset loaded from JSON files. There is no database and no authentication — state lives in the server process and resets on restart.

System architecture

Four layers, one direction of travel. The client owns all presentation and cross-view filter state; the server owns all filtering, aggregation and validation; the data layer is read-only JSON loaded once at import time.

Data flow

The filter bar is the spine of the application. Four filters — Time Period, Warehouse, Category, Order Status — are declared once and drive every view. Changing one triggers this sequence.

  1. User changes a filter FilterBar.vue binds each select straight to a ref from useFilters().
  2. Shared state updates Those refs are declared at module scope in useFilters.js, so all views share one instance — no props, no event bus, no store.
  3. Views react Each view has a watch on the filter refs that re-invokes its loader with getCurrentFilters().
  4. API client builds the request api.js appends only non-'all' values to a URLSearchParams and issues the GET.
  5. FastAPI binds query params Optional typed parameters (warehouse, category, status, month) arrive as function arguments.
  6. Server filters in memory apply_filters() chains warehouse / category / status (case-insensitive, non-mutating), then filter_by_month() matches a YYYY-MM prefix or expands a quarter via QUARTER_MAP.
  7. Pydantic validates the response List endpoints declare response_model, so field drift between JSON and model surfaces as a server-side error rather than bad UI.
  8. Client derives and renders Raw payloads land in refs (allOrders, inventoryItems, summary); every metric is a computed on top — status breakdowns, fill rate, revenue vs. goal — then drawn as hand-rolled SVG.

Architectural notes

  • The client calls two endpoints the server does not implement. api.js defines getTasks, createTask, deleteTask, toggleTask, createPurchaseOrder and getPurchaseOrderByBacklogItem, but main.py has no /api/tasks or /api/purchase-orders route — both return 404. App.vue swallows the failure in a catch and falls back to the hard-coded task list in useAuth.js, so the UI looks functional while every task mutation is silently dropped.
  • Reports.vue bypasses the API client. It imports axios directly and hard-codes http://localhost:8001 twice, so the two /api/reports/* endpoints are the only ones not reachable through the api.js facade — and the only ones that would break if the host changed.
  • Backlog.vue is dead code. The view exists but is neither registered in the router nor imported anywhere; backlog data reaches the UI through BacklogDetailModal on the dashboard instead.
  • Filter coverage is uneven by design. Inventory has no time dimension, so it ignores month; the spending and reports endpoints accept no filters at all and always aggregate the full dataset, even while the global filter bar shows an active selection.
  • Quarter logic is duplicated server-side. Quarter boundaries live in QUARTER_MAP for filtering and are re-derived with a separate if/elif chain inside /api/reports/quarterly.
  • Demo-grade security posture. CORS is allow_origins=["*"] with credentials enabled, there is no authentication or rate limiting, and useAuth returns isAuthenticated = true unconditionally. Suitable for local development only.
